# Changelog
All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [0.0.1] - 2026-08-17

- First release.
- Preview: added a "🎨 Attributes" toolbar button — enabled once a field/constant is selected, same as "🗑 Delete" — that lets you set or clear `TEXT`, `COLOR`, `HIGHLIGHT`, `UNDERLINE`, and (numeric fields only) `EDTCDE` directly from the preview, one keyword per click via a QuickPick, instead of hand-editing the DDS source.
- Fixed: a `PAGNBR` constant couldn't be given an `EDTCDE` from the new "🎨 Attributes" button — `EDTCDE` was only offered for numeric fields, but DDS also allows it on `PAGNBR` (a page number is inherently numeric). The preview's placeholder now also reflects that edit code's width (e.g. `9,999` instead of the plain `9999`), same "worst-case 9s" convention as an edited numeric field. Also fixed `systemKeywordPlaceholder` (`prtf-edit.model.ts`) to recognize `PAGNBR` when it shares its line with another keyword (e.g. `PAGNBR EDTCDE(Y)`) instead of only a bare `PAGNBR` alone.
- Tree view: the "Definition" tree gained its first right-click context menu — "Edit Attributes..." on a field or constant node opens the same TEXT/COLOR/HIGHLIGHT/UNDERLINE/EDTCDE editor as the preview's "🎨 Attributes" button, without needing the preview open. First step towards bringing more of dspf-edit's tree-based editing (record create/delete/copy, indicators) to the tree here too.
- Fixed: a disabled preview toolbar button (e.g. "🗑 Delete"/"🎨 Attributes" before anything's selected) looked identical to an enabled one — the toolbar's own explicit button styling overrode the browser's default disabled dimming. Disabled buttons now render visibly muted, with a "not-allowed" cursor.
- Tree view: added record-level actions — an inline "+" icon on the "📂 Records" row (and "New Record..." on a record's own context menu, ordered before "Copy Record..." and "Delete Record") for creating a record, plus "Copy Record..." and "Delete Record" (with a confirmation naming how many fields/constants go with it). The "Records" row now stays in the tree (labeled with a count, e.g. "📂 Records (0)") even with zero records, instead of a plain "No records found" placeholder, so there's always something to click to create the first one.
- Tree view: added "Indicators..." to a field, constant, or attribute (keyword) node's context menu — add/remove indicators within an AND group (spilling onto continuation lines automatically past DDS's 3-per-line limit, up to 9 ANDed), add/remove a whole OR'd group, or clear everything, via the same one-action-per-click QuickPick convention as "Edit Attributes...". Required a small additive parser/model change (`PrtfField`/`PrtfConstant`/`PrtfAttribute.indicatorLineIndices`) to track which physical lines belong to an element's indicator conditioning — indicator continuation lines precede (not follow) the element they condition, unlike every other DDS continuation convention in this codebase. As a related fix, deleting a field/constant now also removes its own preceding indicator continuation lines instead of leaving them orphaned. Added an indicator example (`TITULO` in `samples/cabecera-report.prtf`) since no sample previously exercised indicators.
- Preview: added an "Indicators" toggle to the toolbar, full parity with dspf-edit's own "Simulate indicators on/off" — a checkbox enables simulation, then a row of per-number buttons (one for every indicator actually referenced in the record being previewed) lets you turn specific indicators on/off to see which fields/constants/keywords would actually print. Gates three things independently: whether an item renders at all, whether a conditionally-applied keyword (`COLOR`/`HIGHLIGHT`/`UNDERLINE`/`TEXT`/`EDTCDE`) on an otherwise-visible item takes effect, and — PRTF-specific, since DSPF has nothing analogous — whether a conditioned `SKIPB`/`SPACEB`/`SPACEA`/`SKIPA` contributes to the running flow position at all, so toggling one visibly shifts everything printed after it. `simulateRecordFlow` (parser) gained an optional `isAttributeActive` gate for this, defaulting to "always active" so every other caller (drag, add, edit-spacing, etc.) is unaffected. An overlaid/background record always renders at the resting state (every indicator off), never the live toggle, matching dspf-edit's overlay behavior. Added a conditioned `SPACEB(2)` (`IN30`) on `CANTIDAD` in `samples/detalle-flujo.prtf` to exercise the SKIP/SPACE case specifically.
- Tree view: added "Copy Field/Constant..." and "Delete Field/Constant" to a field/constant node's context menu — "Delete" reuses the preview's own `deleteElement` (including its indicator-continuation cleanup); "Copy" duplicates the entire block verbatim (`TEXT`/`COLOR`/`HIGHLIGHT`/`UNDERLINE`/`EDTCDE`, indicator conditioning, Line/Position) into a chosen record, except `SKIPB`/`SPACEB`/`SPACEA`/`SKIPA` — which describe the item's position *relative to whatever came before it in the flow*, not a property of the item itself — which you're asked about first. Positioning the copy afterward (either way) is a drag, same as a freshly copied record. Fields get a new-name prompt (validated, unique within the target record); constants don't need one.
- Fixed: the regex behind reading/removing `SKIPB`/`SPACEB`/`SPACEA`/`SKIPA` (`edit-spacing.ts`'s `keywordPattern`, and the parser's own flow-position simulation) required a word boundary before the keyword, which a digit immediately followed by a letter never satisfies — so a keyword written directly abutting a fixed-column zone with no space (e.g. `...+2SPACEB(2)`, the same shape this codebase's own samples already use for `DATE`, as in `...1DATE(*SYS *YY)`) was silently invisible to both. Found while testing the new "Copy Field/Constant..." spacing prompt. Now also matches when immediately preceded by a digit, while still rejecting a letter (so it can't match as a substring of a longer identifier).
- Fixed: the preview's "Overlay" selection was never actually cleared when switching which record is being previewed — only the picker's own option list excluded the active record, not the *stored* target — so a stale overlay from whatever record was active before silently kept applying to the new one. Now reset alongside the "Indicators" simulation state on every record switch.
- Changed how the tree/source/preview stay in sync, to match dspf-edit's own model: selecting a record/field/constant in the "Definition" tree now also points the preview at it directly (`RecordPreviewPanel.syncToLine`, called from the tree's own selection listener), instead of only moving the source cursor and relying on cursor movement to update the preview as a side effect. Moving the cursor around in the source editor on its own no longer changes the preview at all — the `onDidChangeTextEditorSelection` listener that used to drive it (`prtf-edit.listeners.ts`) is gone. Clicking a field/constant inside the preview itself still moves the source cursor and selects it in the tree, and now sets the preview's own selection directly too, rather than depending on the removed listener to loop back. The selected field/constant in the preview is now shown as a border around it (`outline: 2px solid`, matching dspf-edit) instead of a filled yellow background, so the O/6 placeholder text underneath stays legible.
- Preview: clicking blank space on the page (not on any field/constant) now deselects whatever was selected — same as dspf-edit — instead of leaving the previous selection's border and enabled "🗑 Delete"/"🎨 Attributes" buttons stuck showing.
- Preview: reordered the toolbar to match dspf-edit's own layout — row 1 "🗖 Focus"; row 2 "Size:" with Rows/Cols/Overflow and "Overlay"; row 3 "+ Field"/"+ Constant"/"📏 Ruler"/"🗑 Delete"/"🎨 Attributes"; row 4 "Indicators" and "Compose sequence" together. Purely a layout change — no behavior moved.
- Preview: moved the per-number indicator toggle buttons onto their own row (5), shown only once the "Indicators" checkbox is on, and restyled them like dspf-edit's own LED convention — dimmed/grey when off, lit green once toggled on — instead of reusing the plain blue "active" look every other toolbar toggle button has.
- Fixed: dragging a flow-mode field/constant horizontally (column only, same row) could wrongly swap its whole source block with the *previous* field/constant's, scrambling both and stranding the previous item's own indicator-conditioned `SPACEB`/`SPACEA`/`SKIPB`/`SKIPA` at the end of the swapped block. Cause: the drag's own "has this item been dragged above its baseline row?" check (`resolveFlowModeMove`) always assumed every earlier item's conditioned spacing keyword was active, while the page it's dragged within renders with indicator simulation off (resting state) by default — so a preceding item with, say, an `IN30`-conditioned `SPACEB(2)` computed a baseline row taller than what was actually on screen, made an unmoved item look like it had been dragged *above* its own baseline, and triggered the swap meant for that case. `resolveFlowModeMove`/`moveElement` now take the same live indicator-simulation gate the page is currently rendered with, so the baseline always matches the row being dragged within.
- Fixed: dragging a flow-mode field/constant that has its *own* indicator-conditioned `SPACEB` — even purely horizontally, column only — silently stripped that `SPACEB` down to an orphaned "indicator only" continuation line, which then misattached to whatever field/constant came next in the source on the next parse, wrongly making it conditional on that same indicator. Cause: while inactive at rest (its condition not satisfied), a conditioned `SPACEB` doesn't move the item's own rendered row at all — so the row math introduced by the previous fix couldn't tell "this item is exactly on its baseline row because it has no `SPACEB`" apart from "...because its coded `SPACEB` isn't active right now," and rewrote the latter down to 0 on every drag regardless of whether the row actually changed. `moveElement` now also compares the drop point against the item's own currently-*resolved* row (`FlowModeMoveInfo.currentRow`) — when a drag leaves that row unchanged, only Position is rewritten and the item's existing `SPACEB` (active or not) is left exactly as coded.
- Fixed: dragging a flow-mode field/constant *vertically* to a row where its own `SPACEB`/`SPACEA`/`SKIPB`/`SKIPA` value drops to 0 correctly removed the now-unneeded keyword, but — when that keyword's own continuation line also carried an indicator condition (e.g. "IN30 SPACEB(2)") — left the indicator zone behind as a dangling, keyword-less line instead of deleting it outright, which (like the previous bug) then misattached on the next parse to whatever field/constant happened to follow. Same root cause as a fix already made for "Copy Field/Constant..." (`isKeywordZoneBlank` there): the shared `isEmptyKeywordOnlyLine` helper (`move-element.ts`, also used by `editSpacing` and the "🎨 Attributes" editor) required the *entire* line blank, indicator zone included, to consider it safe to delete — so it never actually fired for an indicator-conditioned keyword line, in any of its three callers. Fixed at the source: it now only checks the keyword zone (columns 45-80), matching the reasoning already established for the copy path — which now reuses this same fixed function instead of its own local copy.
- Preview: the "Indicators" checkbox now only appears at all once the record being previewed (or, while composing, any record in the sequence) actually has at least one indicator-conditioned field/constant/keyword to simulate — instead of always showing, and staying checked, even after the last one is removed (e.g. by a drag that strips a record's only conditioned `SPACEB`). Simulation is automatically turned back off and cleared when that happens, so a later record with genuine indicators doesn't inherit a stale "on" state from a previous one.
- Tree view: added "Rename Record..." and "Rename Field..." to a record's/field's own context menu — a single-line rewrite of just the name zone (columns 19-28), same column arithmetic New/Copy Record already use, without touching type/length/decimals/Line/Position or any record-level keywords already coded. Not offered for a constant: unlike a field, a constant has no separate name to rename — its own `name` *is* its literal text or system keyword (e.g. `'Total:'`, `DATE`). No cross-reference fixup needed either way: neither a record format name nor a field name is referenced anywhere else within the same PRTF source (`REFFLD()` only ever points at a field in an externally described database file). Also deduplicated the column-rewrite helper itself — previously copy-pasted verbatim between "Copy Record..." and "Copy Field/Constant..." — into one shared `renameNameZone` (`add-field.ts`) all three rename/copy paths now use.
- Tree view: added "Edit Text..." to a constant's own context menu — the "rename" equivalent for a constant, whose own `name` *is* its literal text rather than a separate identifier. Rewrites just its own text block (definition line through every dash-continuation line — `PrtfConstant.lineIndex..lastLineIndex`) via the same `buildConstantLines` "+ Constant" already uses, at the same Line/Position, splitting across DDS's own keyword-continuation convention again if the new text needs it; any `COLOR`/`HIGHLIGHT`/`UNDERLINE`/`EDTCDE`/`SPACEB`/indicator conditioning the constant carries lives on separate lines past that range and is left untouched. Only offered for a plain quoted literal — a hex literal (`X'...'`) or a bare system keyword (`DATE`/`TIME`/`PAGNBR`) shows an explanatory message instead, since neither has literal text to edit this way. Doesn't attempt to reposition anything after the edited constant if its length changes — same "edit in place, then drag if needed" scope already agreed for "Copy Field/Constant..."'s SKIPB/SPACEB question; anything still coded with a relative `"+n"` Position elsewhere in the record re-resolves against the new length automatically on the next parse regardless.
- Tree view: added "Fill to Width of..." to a constant's own context menu — pads its literal text with trailing spaces to match another field's or constant's printed width, picked from anywhere in the document (not just its own record — e.g. a header label matching a detail record's field width below it, the case this was built for). A one-shot pad, not a persistent link: existing trailing spaces are trimmed before padding back to the target width, so running it again against the same (or a narrower) target doesn't accumulate extra spaces, but a later change to the target's own width needs a re-run to follow it. Reuses "Edit Text..."'s own write path (`replaceConstantText`, factored out of `edit-constant-text.ts`) and the parser's own printed-width estimate for a constant (`constantPrintedWidth`, moved into `model.ts` alongside `stripConstantQuotes` so both the parser's "+n" chaining and this feature's target-width lookups share one implementation). Same eligibility as "Edit Text...": not offered for a hex literal or system keyword, which have no literal text to pad.
- Fixed: a numeric field target for "Fill to Width of..." used its raw DDS length as the width to match — but an `EDTCDE`-edited field (comma grouping, a `CR`/`-` sign) prints wider than its raw digit count, e.g. a 7,2 field with `EDTCDE(J)` prints as `99,999.99-` (10 characters), not 7. Now reuses the preview's own "worst case" edited-width estimate (`editedNumericPlaceholder`, exported from `record-preview-panel.ts`, same `EDIT_CODES`/comma-grouping/sign logic the preview itself renders with) when the target field has a recognized `EDTCDE`, falling back to its raw length otherwise.
